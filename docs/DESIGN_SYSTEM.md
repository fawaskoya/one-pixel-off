# Design system — implemented inspection lab

This document distinguishes the current CSS/component baseline from release-quality roadmap requirements. It must not imply unimplemented interaction behavior.

## 1. Direction

One Pixel Off uses a dark editorial inspection-lab aesthetic: ink canvas, off-white vector boards, acid-lime signal, coral misses/urgency, cobalt notices, mono numerals, square puzzle cells, and restrained hard-edged depth.

Avoid toy/casino styling, fake hacker terminals, stock illustration, glass-heavy panels, and decorative motion around the timed board.

The product name remains a working title. “One pixel” is metaphorical. Geometry
mutations use 4–12 view-box units, non-scaling stroke mutations use 1–4 width
units, and stripe rotation mutations use 6–12 degrees, depending on difficulty.

## 4. Page shell and routes

Implemented content widths:

- `.shell`: up to 1180 px with 40 px total outer subtraction.
- `.reading-shell`: up to 740 px.
- `.pixel-game-shell`: up to 760 px.
- `.pixel-stage`: up to 760 px.

The global site header/footer remain part of the App Router layout. Game pages use the same shell; `body.game-active` styling exists in CSS but the current GameShell does not toggle that class.

Current routes:

- home `/`;
- play `/play` and `/play?mode=daily`;
- dynamic challenge `/challenge/[token]`;
- how-to, Pattern Lab (`/categories`), about, privacy, terms, contact;
- offline fallback.

There is no separate Daily or Stats page.

## 5. Home baseline

The home page includes:

- working-title hero and “Start the scan” link;
- static 6×6 demonstration board;
- five-round/15-second/local-generation facts;
- three-step rules;
- conceptual pattern cards;
- disabled-by-default `AdSlot` boundary;
- deterministic/no-AI explanation;
- FAQ and final CTA.

The demonstration is not generated by the domain and is not interactive/scored.

On desktop viewports at or below 880 px tall, the hero uses the remaining dynamic viewport below the 79 px header. Its headline responds to both inline and block size, its vertical rhythm compacts, and the demo-card wrapper reserves space for rotation and shadow. Taller desktop layouts retain the full-scale composition; tablet and mobile layouts remain naturally scrollable rather than clipping or scaling the entire section.

## 6. Setup baseline

`GameShell` uses component state `null` as setup. It provides:

- Quick/Daily radio cards on `/play`;
- a locked Challenge variant when a decoded seed exists;
- setup error alert;
- five-board/15-second/one-anomaly facts;
- “Prepare scan” or “Accept challenge”.

Session preparation is synchronous. There is no reducer `home`, `preparing`, or error phase.

## 7. Ready baseline

Implemented `ready` view shows:

- round progress track;
- mode label;
- round number and difficulty;
- “Eyes ready?” heading;
- hidden-board explanation;
- explicit Start button.

The puzzle board is not rendered in this phase. Starting dispatches guarded `START_ROUND` with `Date.now()`.

## 8. Playing baseline

Order:

1. Round track and unique wrong count.
2. Timer in tenths.
3. Timer rail.
4. Puzzle frame/board.
5. Polite wrong-count feedback.

The board is square and uses `repeat(gridSize, 1fr)` for `gridSize` 4, 5, or 6. It has a 2 px dark gap and each cell is square.

Current cell behavior:

- native `<button>`;
- label `Tile <row>, <column>`;
- SVG is `aria-hidden` and `focusable=false`;
- normal browser Tab order includes every enabled cell;
- Enter/Space use native button click;
- no arrow-key/roving focus behavior;
- hover mixes the background with signal;
- wrong cell adds a 2 px coral inset border through `::after`;
- target marker does not exist until `round_result` and adds a 3 px signal-deep inset border;
- target/non-target visual geometry differs only through generated SVG data before reveal.

Puzzle cells inherit their size from the square board with no intrinsic minimum that can force grid overflow. The active frame has a 590 px desktop cap and subtracts a conservative HUD/timer reserve from dynamic viewport height. At the 320 px portrait reference width, 6 px safe gutters and compact frame padding preserve approximately 46 px cells for a 6×6 board; unusually short viewports may reduce that size to keep the complete board visible.

## 9. Timer baseline

- UI interval dispatches every 100 ms while `playing`.
- Display is `(remainingMs / 1000).toFixed(1)`.
- Numeric label uses `ceil(remainingMs / 1000)` seconds.
- At 5 seconds or less, timer and rail switch to coral.
- Rail width transitions over 100 ms.
- Reducer deadline, not the rendered number, determines timeout.
- The timer itself is not a live region; wrong feedback is `aria-live=polite`.

Reduced-motion CSS reduces all transition/animation durations to `0.01ms` and removes button hover transform.

## 10. Wrong selection baseline

On a first unique wrong selection:

- reducer appends the cell index;
- coral inset border appears;
- HUD/live feedback count updates;
- play and clock continue.

Repeated activation of the same wrong cell changes no wrong index/score, though reducer time can advance. Current wrong styling uses color/border only; adding a redundant non-color mark is roadmap accessibility work.

## 11. Round-result baseline

Implemented `round_result`:

- check or × result mark;
- “Anomaly found.” or “Time exposed it.”;
- remaining time for found or target-reveal copy for timeout;
- `+<score> points`;
- disabled board with wrong cells retained and target outlined;
- Next board / See scan report action.

The result overview and disabled review board share a two-column workspace on tablet/desktop and short landscape. Narrow portrait screens use a compact status grid above a dynamic-viewport-constrained review board, keeping the action in the same contained panel.

The explanation exposes only mutation kind (`offset`, `size`, `spacing`, `stroke`, or `rotation`), not primitive/field/from/to detail.

This state contains no ad component.

## 12. Session-result baseline

Implemented `session_result` shows:

- outcome-dependent heading;
- found count;
- total local score;
- total unique wrong taps;
- challenge, new Quick, and Daily actions;
- native-share/clipboard/manual-copy feedback.

It does not display per-round strips, median time, local history, streak, preference controls, or an ad.

## 13. Sharing baseline

Challenge URL is `/challenge/<opo1 token>`. Share text includes the current local score; token payload does not. Capability order is native share, clipboard, then a read-only selectable URL. User cancellation reports “Sharing cancelled.”

## 14. Responsive baseline

Implemented breakpoints:

- min 901 px / max 880 px tall: landing hero adopts a viewport-height budget, height-aware heading, compact spacing, and a height-constrained demo card with reserved decoration space.
- max 900 px: editorial grids collapse/refit.
- max 700 px: a 60 px header, safe-area-aware 6 px active-play gutters, a width-first board capped at 430 px, compact HUD/timer spacing, two-up mode cards, three-up fact/stat strips, a one-column result workspace, and a two-row summary action grid.
- max 380 px: compact brand/hero, tighter setup cards, and fluid active/review boards constrained by available inline and dynamic viewport size.
- short landscape (`max-height:620px`): a 56 px compact header and reduced play chrome preserve a larger height-constrained board; the round result stays two-column and the session summary becomes a two-column report.

Coarse/touch input uses `touch-action: manipulation`, removes sticky hover treatment, and applies a distinct pressed state. Mobile game padding respects left, right, and bottom safe-area insets.

All transactional shells, panels, grid tracks, copy, buttons, and manual-share inputs use explicit width containment. Setup and summary remain document-scrollable when content or user zoom genuinely exceeds the available block size; controls must never be clipped or create horizontal page overflow.

Any stronger claim—such as full 200% zoom compliance—requires browser evidence and is currently a QA target, not a completed contract.

## 15. Forced-colors baseline

Current forced-colors CSS:

- applies `2px solid CanvasText` borders to buttons/cards/panels/puzzle frame/cells;
- maps brand/round indicators to CanvasText;
- maps active/completed indicators to Highlight.

It does not currently add explicit forced-color differentiation for `data-wrong` and `data-target` pseudo-elements. Verify and improve before claiming complete high-contrast parity.

## 16. Accessibility status

### Implemented

- Skip link and global focus-visible outline.
- Semantic buttons, radio inputs, fieldset/legend, headings, links.
- Named pattern group and row/column cell labels.
- Native keyboard activation.
- Polite wrong-count feedback and result/share status/alerts.
- Reduced-motion and basic forced-colors CSS.
- SVGs hidden from the accessibility tree so target metadata is not announced.

### Roadmap / not implemented

- Roving tab stop and arrow-grid navigation.
- Redundant non-color wrong/target markers verified in forced colors.
- Rich target explanation tied to focus/announcement.
- Bounded start/five-second/timeout announcements.
- Focus movement on phase changes.
- Verified 44 px minimum at all breakpoints.
- Documented screen-reader and 200% zoom evidence.

Agents must not describe the roadmap list as shipped.

## 17. PWA/offline baseline

Manifest is implemented. Production registration occurs after page load. The service worker precaches only `/offline` and `/icon.svg`, then provides network-first navigation with offline-page fallback.

There is no install prompt, cached-shell guarantee, phase-aware update UI, or deferred `skipWaiting`. The offline page accurately says Quick may work if the browser already cached play assets.

## 18. Advertising baseline

Home contains one `AdSlot`. It returns null unless `NEXT_PUBLIC_ADS_ENABLED=true`; when enabled it is only a labeled reserved placeholder. No game state renders it. No Google ad script or consent UI is implemented.

Roadmap rules for a real integration:

- require current policy research, approval, privacy/consent review, and explicit authorization;
- keep `ready`, `playing`, and `round_result` free of ads;
- separate ads from puzzle-like cards, navigation, and primary actions;
- reserve layout space and verify failure/no-consent behavior.

## 19. Voice and copy

Implemented voice is technical but playful: “Choose your scan,” “Eyes ready?”, “Anomaly found,” “Time exposed it,” “Sharp scan.”

Keep claims factual:

- No AI/image API per puzzle.
- Results stay local through current application code.
- Same supported seed/version reproduces boards.
- Scores are local and editable, not authoritative.
- Offline play is conditional, not guaranteed.

Avoid IQ, medical, eyesight diagnosis, guaranteed traffic/income, “impossible,” or literal-one-hardware-pixel claims.

## 21. Definition of design done

For changes to the implemented baseline, verify all affected phases at square sizes 4, 5, and 6; pointer and native keyboard input; normal/reduced motion; normal/forced colors; narrow/landscape/desktop layouts; wrong/found/timeout; share and storage failures. Report known roadmap limitations rather than silently marking them complete.
